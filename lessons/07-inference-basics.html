1. Concepts

The two phases: prefill and decode

  • Prefill: process the full input prompt of length P in one batched forward pass. Lots of tokens → high arithmetic intensity → compute-bound. Produces the first output token + the initial KV cache.
  • Decode: generate output tokens one at a time. Each step processes just 1 new token but must read the entire weight matrices and the growing KV cache from HBM → memory-bound. This dominates wall time for long generations.

KV cache: why and what

Naively, generating token T+1 would re-compute attention over all T previous tokens (and recompute their K/V). Instead, we cache K and V for every past token at every layer. At step T+1, only one new (Q, K, V) triple is computed; new K, V are appended; attention runs against the cache.

KV cache memory size for one request:

\[M_{\mathrm{KV}}=2\cdot n_{\mathrm{layers}}\cdot n_{\mathrm{kv\ heads}}\cdot d_{\mathrm{head}}\cdot L\cdot\operatorname{bytes}_{\mathrm{elt}}\]

The factor 2 = K and V. Multiply by batch size for concurrent requests.

Real-world: LLaMA-2-7B has 32 layers, 32 KV heads, d_head=128. At 4096 ctx, FP16 (2 bytes): 2·32·32·128·4096·2 = ~2.1 GB per request. At batch=32, that's 67 GB — bigger than the 14 GB of weights!

Sampling strategies

  • Greedy: always pick argmax token. Deterministic, often dull/repetitive.
  • Temperature T: scale logits by 1/T before softmax. T<1 sharpens (more deterministic), T>1 flattens (more diverse). T=0 ≡ greedy.
  • Top-k: keep only the k highest-probability tokens, renormalise, sample.
  • Top-p (nucleus): keep the smallest set of tokens whose cumulative prob \(\ge p\) (e.g., 0.9), renormalise, sample. Adapts the cut-off per step.

Latency vs throughput

  • Latency: wall time per request (TTFT = time to first token; TPOT = time per output token).
  • Throughput: tokens generated per second across all concurrent users.

Batching multiple requests improves throughput (amortises weight loads) but increases each request's TTFT. The whole inference-systems field is about navigating this trade-off (next lesson).

2. Socratic check

Why is decode memory-bound while prefill is compute-bound?

Prefill processes P tokens at once → big matmuls with high arithmetic intensity. Decode processes 1 token → matmuls degenerate to vector × matrix; you must load entire weight matrices to multiply against a single token vector → low AI → bandwidth-limited.

Why cache K and V but not Q?

Past Q values are never reused — each decode step only needs the new Q dotted against all past K. K and V, however, must be re-read every step → caching them avoids recomputation.

You batch 64 users. What grows and what stays the same?

Weight loading per step stays the same (one copy of weights). KV cache memory grows 64×. Per-step compute grows 64× but is still vector-ish until batch saturates compute — so throughput rises sharply while latency rises only mildly. This is why batching is the #1 throughput lever.

Key Takeaways

  • Prefill = compute-bound (parallel over P tokens). Decode = memory-bound (1 token, full weight read).
  • KV cache: M = 2·L·H_kv·d_h·N·bytes per request — often bigger than the weights.
  • Sampling: greedy → top-k → top-p → temperature; mix and match.
  • Batching trades latency for throughput; the systems lessons fix the trade-off.
